How the Seller Agent Console works

A PSP-hosted control plane that lets a merchant run AI agents against their Amazon seller account without handing them the keys. Agents propose; a policy engine (the Mandate Gate) decides what is even eligible; a human approves; only approved writes reach the Selling Partner API. Shopper-facing agents sell inside Claude, ChatGPT and Gemini under the same mandates, and checkouts clear through the PSP's agentic-payments rails.

1 · Seller-side control loop

Pricing, Listing and Restock agents run as custom agents (Quick / Claude / Seller Assistant workflows). Every proposal goes through the Mandate Gate. In-mandate proposals queue in the inbox; out-of-mandate proposals are auto-blocked and only ever appear in the audit log.

2 · Shopper-side: agents as plugins for Claude, ChatGPT and Gemini

The same agent definitions are published as a Claude MCP connector, a ChatGPT app (Apps SDK, with ACP checkout) and a Gemini extension. The Storefront Agent answers shoppers grounded only in listing data, and can only make offers the mandate allows. Payment runs through Meridian Pay's agentic checkout (AP2 mandates / ACP), so the merchant never shares card acceptance with the assistant vendor.

3 · Components

Console (this prototype)

  • Agent roster — status, published surfaces, goal, 7-day metrics; pause / resume / edit; new-agent wizard.
  • Mandate Gate — evaluateProposal() runs every rule, returns per-check pass/fail. Changing a mandate re-evaluates every open proposal (blocked ↔ pending).
  • Proposal inbox — Approve (dispatches a write, confirms asynchronously), Edit (live gate feedback; cannot save out-of-mandate), Decline (reason captured).
  • Conversations — transcripts per surface, outcome, escalation resolution.
  • Sales & payments — GMV by surface, Featured Offer status, stock vs floor, PSP auth metrics.
  • Insights — what works / what doesn't, each with an action that lands on the relevant proposal or agent.
  • Copilot — chat + Web Speech voice; intents call the same functions as the buttons and write to the audit log as the owner.

Agent runtime

  • One agent definition (goal, tools, mandate scope) compiled to three plugin manifests: MCP server (Claude), Apps SDK app with ACP checkout (ChatGPT), Extension (Gemini).
  • Seller-facing agents (Pricing, Listing, Restock, Ads) are reachable by the seller from the same assistants — "ask Pricing Agent in Claude".
  • Shopper-facing agents (Storefront, Support) are reachable by shoppers; they only read catalog/orders and can only offer what the mandate allows.
  • Tools are role-scoped OAuth grants on SP-API; *:write tools are only callable from an approved proposal.

Approval flow

1
ProposeAgent emits a typed proposal (price_change · restock · listing_update · discount_offer) with rationale.
2
GateMandate Gate evaluates. All checks pass → inbox. Any fail → auto-block, audit log, never actionable.
3
DecideOwner approves, edits (re-gated live) or declines — in the console or via Copilot chat/voice.
4
WriteApproved proposal → Selling Partner plugin (MCP) or Seller Assistant workflow → SP-API with role-scoped OAuth.
5
ObserveSP-API signals and PSP payment events stitch back onto the proposal / conversation in the audit log and feed Insights.
